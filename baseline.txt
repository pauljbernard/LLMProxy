LLM Proxy Learning System

Architecture, Requirements, and Integration Specification

1. Purpose

Build a local-first LLM proxy and learning pipeline that turns high-value model interactions into durable local capability.

The system has two primary responsibilities:

1. Serve as an OpenAI-compatible runtime proxy for local models, closed-source teacher models, coding agents, IDEs, CLIs, and other tools.
2. Capture, validate, export, train, evaluate, and redeploy improved local models through a controlled learning loop.

The objective is not to create a frontier model.

The objective is to create smaller, cheaper, private, local, domain-specialized models that improve over time from:

* teacher-model expertise
* validated runtime interactions
* repository-specific patterns
* personal coding and architecture preferences
* Common Lisp and Smalltalk knowledge
* agent-system design patterns
* investment reasoning frameworks
* writing and explanation style

The system should allow local models to become progressively more useful within targeted domains while preserving auditability, quality gates, rollback capability, and runtime stability.

⸻

2. Core Concept

The system consists of a runtime proxy, a training pipeline, and an integration layer.

User / IDE / CLI / Coding Agent
        ↓
OpenAI-Compatible LLM Proxy
        ↓
Routing / Policy / Evaluation / Recording
        ↓
Local Models + Closed Teacher Models + Tools
        ↓
Training Candidate Store
        ↓
Approved Dataset Export + Manifest
        ↓
Learner Training Pipeline
        ↓
LoRA / QLoRA Fine-Tuning
        ↓
Evaluation + Promotion Gate
        ↓
Model Registry + Deployment
        ↓
Proxy Routing Update
        ↓
Improved Local Model

The proxy should not merely answer questions.

The learner should not merely train models.

Together they form a controlled learning system.

The proxy converts expensive model intelligence into reusable local capability.

⸻

3. System Goals

3.1 Runtime Goals

The system must:

* expose an OpenAI-compatible /v1/chat/completions endpoint
* expose /v1/models
* optionally expose /v1/embeddings
* route requests to local or remote models
* support streaming responses
* support domain-aware routing
* support local inference engines
* support closed model providers through adapters
* preserve request and response metadata
* record selected interactions as training candidates

Supported local runtimes should include one or more of:

* Ollama
* llama.cpp server
* vLLM
* LM Studio
* MLX-LM / MLX server

Supported teacher/provider adapters should include:

* OpenAI-compatible providers
* Anthropic-compatible providers
* Google Gemini-compatible providers
* DeepSeek-compatible providers

⸻

3.2 Distillation Goals

The system must:

* record selected interactions as training candidates
* query multiple teacher models for hard tasks
* synthesize improved answers from teacher outputs
* score responses using judge models and rule-based validators
* preserve all teacher outputs and critiques
* export approved examples as JSONL
* support separate datasets by domain and target adapter
* prevent unapproved or low-quality data from entering training

⸻

3.3 Training Goals

The learner pipeline must:

* consume approved proxy exports
* validate dataset integrity
* support domain-specific datasets
* support deterministic dataset versioning
* support LoRA fine-tuning
* support QLoRA fine-tuning
* support multiple base models
* support repeatable training runs
* support checkpointing
* store artifacts
* register trained adapters
* evaluate every trained model
* compare against base models and previous local versions
* prevent bad models from promotion

⸻

3.4 Deployment Goals

The system must:

* publish approved models to local runtimes
* register deployed models with the proxy
* support model aliases
* support routing by domain and task type
* support shadow deployment
* support canary deployment
* support production promotion
* support rollback
* preserve prior production models

⸻

4. Non-Goals

The first version does not need to:

* train frontier-scale foundation models
* support large distributed multi-node training
* implement RLHF
* implement full preference optimization
* support every LLM provider
* support every training framework
* replace a full MLOps platform
* perform autonomous investment decisions
* execute financial transactions
* guarantee factual correctness without validation
* implement enterprise-grade multi-user security

⸻

7.3 Routing Policy Engine

The routing engine decides where a request goes.

Routing modes:

local_only
teacher_single
teacher_ensemble
local_then_teacher
teacher_then_local
judge_only
record_only

Example rules:

If domain = coding and complexity = low:
    route to local coding model
If domain = software_architecture and complexity = high:
    query teacher ensemble
If domain = investment_analysis:
    use teacher ensemble and require critique
If privacy = high:
    use local_only
If record_training_candidate = true:
    synthesize, score, and persist candidate

All model providers must implement a common interface.

7.5 Teacher Ensemble

For selected requests, the proxy should ask multiple teacher models.

Process:

1. Send the normalized prompt to Teacher A, Teacher B, and Teacher C.
2. Collect all answers.
3. Ask a judge model to compare outputs.
4. Produce a synthesized best answer.
5. Store all teacher outputs.
6. Store the judge critique.
7. Mark the synthesized answer as a training candidate if eligible.

Output should include:

final_answer
teacher_outputs
judge_critique
chosen_rationale
quality_score
training_eligibility
training_candidate_id

⸻

7.6 Judge and Critic Layer

Evaluate responses by:

* correctness
* completeness
* technical depth
* architectural soundness
* clarity
* style match
* testability
* risk awareness
* domain fit

For code, also evaluate:

* compiles
* tests pass
* minimal change
* follows repository conventions
* security risk
* performance risk

For investment analysis, evaluate:

* causal reasoning
* scenario structure
* assumption clarity
* second-order effects
* risk balance
* avoidance of unsupported predictions

10. Learner Pipeline Components

10.1 Dataset Ingestion

Responsibilities:

* scan configured export directories
* import JSONL files
* validate manifest
* validate checksums
* persist dataset metadata
* detect duplicate imports
* assign dataset version IDs

Supported import modes:

file_drop
api_import
event_triggered_import

API endpoint:

POST /datasets/import

Example request:

{
  "dataset_export_id": "dsexp_20260605_772ab",
  "manifest_path": "/proxy_exports/architecture-adapter-20260605.manifest.json",
  "data_path": "/proxy_exports/architecture-adapter-20260605.jsonl"
}

⸻

10.2 Dataset Validation

Validation rules:

* record must contain messages
* messages must contain user and assistant turns
* assistant response must be non-empty
* metadata must contain domain
* metadata must contain task type
* quality score must meet configured threshold
* approval status must be approved
* export eligible must be true
* record must not be rejected or blocked

Optional validation:

* no secret leakage
* no API keys
* no credentials
* no private keys
* no binary blobs
* no malformed code fences
* max token length not exceeded

Records failing validation must be quarantined.

⸻

10.3 Dataset Normalization

Responsibilities:

* normalize whitespace
* normalize role order
* standardize system prompts
* remove proxy-only metadata
* preserve domain metadata
* preserve provenance
* truncate examples exceeding configured token limits
* optionally split long conversations into smaller examples

Example domain-specific system prompt:

You are a senior Common Lisp, SBCL, and distributed systems engineer.

⸻

10.4 Deduplication

Deduplicate at three levels:

* exact duplicate
* near duplicate
* semantic duplicate

Techniques:

* SHA-256 hash for exact text
* MinHash or SimHash for near duplicates
* embedding similarity for semantic duplicates

Default rule:

If similarity > 0.95, keep the higher-quality example.

⸻

10.5 Dataset Splitting

Create stable deterministic splits:

train:      90%
validation: 5%
test:       5%

Use:

hash(proxy_candidate_id or normalized_prompt)

The same example must always land in the same split unless the dataset version changes.

⸻

10.6 Curriculum Builder

Support staged and weighted training.

Example weighted sampling:

coding                  35%

common_lisp             10%
smalltalk               10%
agent_systems           10%
investment_analysis      7%
writing_style            3%

14. Promotion Gate

A model may only be promoted if:

* all required evaluations complete
* overall score meets threshold
* domain score meets threshold
* no critical regressions
* latency is acceptable
* memory usage is acceptable
* artifacts are verified

Example thresholds:

promotion:
  min_overall_score: 0.85
  min_coding_pass_rate: 0.80
  min_architecture_score: 0.85
  min_style_score: 0.80
  max_regression_allowed: 0.02

Training states:

created
queued
training
failed
completed
evaluating
candidate
approved
rejected
deployed
rolled_back
retired

A model may not enter approved unless evaluation succeeds.

A model may not enter deployed unless deployment health checks succeed.

15. Deployment and Routing

After approval, the learner deploys the model to a local runtime and registers it with the proxy.

Proxy registration endpoint:

POST /proxy/models/register

Example payload:

{
  "model_registry_id": "model_paul_architecture_v1",
  "model_alias": "paul-architecture-local-v1",
  "base_model": "Qwen/Qwen2.5-Coder-14B-Instruct",
  "adapter_type": "lora",
  "adapter_path": "/models/adapters/paul-architecture-v1",
  "runtime": "ollama",
  "endpoint_url": "http://localhost:11434",
  "domains": [
    "software_architecture",
    "coding"
  ],
  "task_types": [
    "architecture_decision",
    "code_review"
  ],
  "quality": {
    "overall_score": 0.88,
    "domain_scores": {
      "software_architecture": 0.90
    }
  },
  "status": "production",
  "created_at": "2026-06-05T12:00:00Z"
}

The proxy must support these deployment strategies:

manual
shadow
canary
production
rollback

Shadow mode:

Production model answers the user.
Candidate model receives copied traffic silently.
Proxy compares candidate output against production and teacher output.

Canary mode:

Candidate model receives limited real traffic.
Example: 10% of eligible architecture prompts.

Production mode:

Candidate model becomes default for its domain.

Rollback mode:

Prior production model is restored.
Routing policy is reverted.
Rollback event is logged.

* redact secrets from logs

26. Failure Handling

Proxy Export Failure

If export fails:

* candidate statuses remain approved
* no dataset export event is emitted
* error is logged
* retry is allowed

Learner Import Failure

If import fails:

* dataset is marked failed
* invalid records are quarantined
* proxy is notified
* training is not started

Training Failure

If training fails:

* training run status becomes failed
* artifacts are retained for inspection
* proxy remains unchanged
* training.failed event is emitted

Evaluation Failure

If evaluation fails:

* model cannot be promoted
* training run status becomes evaluation failed
* proxy remains unchanged

Deployment Failure

If deployment fails:

* model status becomes deployment failed
* proxy routing remains unchanged
* rollback is not required

Runtime Failure

If deployed model fails:

* proxy falls back to previous model or teacher
* failure event is emitted
* rollback may be triggered

28. Design Principle

The system exists to convert valuable interactions into durable capability.

The proxy captures and validates expertise.

The learner pipeline converts that expertise into trainable datasets.

The training system produces local specialist models.

The evaluation system prevents regressions.

The deployment system introduces improved models safely.

The routing system controls exposure.

The rollback system preserves stability.

The long-term goal is to create local models that encode:

teacher-model expertise
+
personal domain judgment
+
repository-specific knowledge
+
validated coding behavior
+
architecture reasoning
+
investment reasoning frameworks
+
writing and explanation style

The result should be smaller, cheaper, local, private, domain-specialized models that improve continuously without compromising runtime reliability.

The proxy should not simply call models.

The learner should not simply train models.

Together they should form a reliable, auditable, reversible, self-improving learning system.
